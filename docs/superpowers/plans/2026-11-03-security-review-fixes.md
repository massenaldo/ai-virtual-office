# Security review fixes (3B.5 prerequisite) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox syntax.

**Goal:** Close the findings of the independent security review (`docs/security-review-3b5.md`) that matter before the Claude agent may write on a real workspace: H1, M1, M2, M3, L1 (L2, L3, L4 and the Info items are recorded, not fixed here).

**Architecture:** Four independent changes in the existing server: (1) redaction applied to whole files before they are sliced or searched, and more secret formats; (2) Unicode-safe name comparison for the sensitive-path denylist and path patterns, a wider denylist, and stricter workspace-layout checks at startup; (3) "execution-sensitive" paths (files that tools run on their own) can only be approved once, server-enforced and shown in the UI, plus queued requests are asked again when a broader permission is granted; (4) task and agent permissions made from an approval are bound to the workspace they were made in.

**Tech Stack:** TypeScript, Node, vitest, existing permission engine (`server/permissions/*`), task manager (`server/taskManager.ts`), policy (`server/toolPolicy.ts`), file operations (`server/fileOps.ts`), React UI (`src/workforce/*`).

**Spec:** `docs/security-review-3b5.md` (findings H1, M1, M2, M3, L1 with where, attack, fix). Read the finding for your task there first.

## Global Constraints

- The security properties of 3B.4 and 3B.5.1-3 must not weaken: every existing test keeps passing unless a test pinned the exact behaviour a finding says is wrong (then change that test deliberately and say so in your report).
- No new dependency. No `child_process`, `exec(`, `spawn(`, `fork(`, `worker_threads` in `server/`, `src/` or `scripts/` (a repo test scans them).
- Errors shown to people are fixed sentences; no host path, no content, no secret in any error, log, audit line or event.
- The browser is never an authority: the server enforces every rule; the UI only reflects it.
- Match the codebase style: short comments that say why, conventional commits ending with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.
- Verification at the end of each task: its own tests, `npx tsc -b`, and `npx vitest run server/noProcessExecution.test.ts`; once at the end `npm test`.

## Review Focus

1. A way to see key material, a secret or a denylisted file's content that the changed code still allows (M1, M2, L1).
2. A write to an execution-sensitive file made without a fresh approval of exactly that change, by any scope, rule or queue path (H1).
3. A grant that still applies in a workspace other than the one it was made in (H1).
4. Existing permission files, existing tests and the UI keep working (old `permissions.json` loads; mock runtime unchanged).

### Task 3: Execution-sensitive paths are approved once, queued requests are asked again, the label tells the truth (H1 a, c, d)

**Files:** Create `server/execSensitive.ts`; Modify `server/taskManager.ts`, `src/workforce/types.ts`, `src/workforce/storage.ts`, `src/workforce/api.ts` (only if the pending-approval shape is validated there), `src/workforce/view.ts`, `src/workforce/ui/ApprovalChoiceForm.tsx`; Test `server/execSensitive.test.ts`, extend `server/e2e/claudeWrites.test.ts`, `server/taskManager.test.ts`, `src/workforce/view.test.ts`, `src/workforce/ui/ApprovalChoiceForm.test.tsx`, `src/workforce/storage.test.ts`.

**Interfaces:**
- Produces `isExecSensitive(relative: string, workspacePath: string): boolean` in `server/execSensitive.ts`: true when the folded relative path (use `foldName` from `server/sensitivePaths.ts` if Task 2 is done, else `toLowerCase`) has a segment or basename matching: `package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `.pnpmfile.cjs`, `pnpm-workspace.yaml`, `makefile`, `gnumakefile`, `*.mk`, `justfile`, `taskfile.yml`, `taskfile.yaml`, `dockerfile`, `docker-compose*.yml`, `docker-compose*.yaml`, `conftest.py`, `setup.py`, `setup.cfg`, `pyproject.toml`, `tox.ini`, `noxfile.py`, `build.gradle`, `build.gradle.kts`, `pom.xml`, `cargo.toml`, `build.rs`, `go.mod` (no: keep this list), `*.sh`, `*.bash`, `*.zsh`, `*.ps1`, `*.bat`, `*.cmd`; any path under a segment `.husky`, `.githooks`, `.claude`, `.vscode`, `.idea`, `.github`, `.gitlab`, `.circleci`, `.devcontainer`; the files `.gitlab-ci.yml`, `.mcp.json`, `claude.md`, `agents.md`; AND any existing regular file (not a symlink) inside the workspace whose mode has an execute bit (`lstat`; a missing file is only judged by its name). Never throws: any error means `true` (fail closed).
- Produces a `onceOnly: boolean` field on a pending approval (`PendingApproval` in `src/workforce/types.ts`), set by the server for Write and Edit on an execution-sensitive path, `false` otherwise; carried through state, events and the browser's storage validation like the other fields (missing in older saved state means `false`).

- [ ] Server (`server/taskManager.ts`): in `approveTool`, for the write tools (`Write`, `Edit`), compute `onceOnly = isExecSensitive(relative, workspace.path)` from the policy's checked path. If the permission decision is an `allow` whose source is not `once` (a task, agent or global rule), treat it as `ask` when `onceOnly` (so a standing rule never silently allows such a change). The pending approval records `onceOnly`. In `decideApproval`, an approve with a scope other than once for an `onceOnly` approval is refused with code `invalid` and the sentence `Changes to files that tools run on their own can only be allowed once.`. In `permitTool` (the use-time check), an allow whose source is not `once` is refused for `onceOnly` actions (audit reason `exec_sensitive`), so a rule added or changed after the question cannot widen it.
- [ ] Queue (`promote` and `approveTool`): when a decision grants a non-once rule (task or agent scope), every request that was already waiting in the queue at that moment must be asked again for a person rather than allowed by that new rule: pass the id of the rule just granted through `promote` into `approveTool` and treat an allow from exactly that rule as `ask` for queued requests only. Requests made after the decision are allowed by the rule as before.
- [ ] UI: `allowedScopes`/the approval choice shows only "Once" when the pending approval is `onceOnly`, with the hint `Changes to files that tools run on their own (for example package.json, scripts, git hooks, editor and CI settings) can only be allowed once.`; the "this task"/"this agent" description text in `src/workforce/view.ts` currently says each call "is still checked and recorded": change it to say plainly that later changes under that permission are **not shown to you again** (keep it short and update the tests that pin the text).
- [ ] Tests, all failing first: unit tests of `isExecSensitive` (every listed name, nested path, a `.sh` at depth, an existing file with mode 0755 named `run`, a 0644 `notes.txt` is false, a symlink is judged by name, an error path is true); e2e (`server/e2e/claudeWrites.test.ts` helpers): `vo_write package.json` with `allow_task` and with `allow_agent` is refused with the sentence and nothing is written, with `allow_once` it is written; `.husky/pre-commit`, `.claude/settings.json`, `scripts/build.sh`, and an existing 0755 file all behave the same; with a global `allow` rule for Write a write to `package.json` still asks while a write to `notes.txt` does not; after "this task" on `notes.txt`, a later write to `package.json` in the same task still asks; **queue:** two writes `a.txt` and `b.txt` made at once, the first approved with `allow_task`, the second is asked again (task stays waiting, a new approval appears) and is only written after its own approval; the pending approval carries `onceOnly` true/false correctly; the UI component test shows only Once for `onceOnly`; older saved state without the field loads.

### Task 4: Task and agent permissions made from an approval belong to one workspace (H1 b)

**Files:** Modify `server/permissions/types.ts`, `server/permissions/engine.ts`, `server/permissions/storage.ts`, `server/permissions/store.ts`, `server/permissions/view.ts`, `server/taskManager.ts`, `src/workforce/api.ts`, `src/workforce/permissions.ts`, `src/workforce/ui/PermissionRuleRow.tsx`; Test `server/permissions/engine.test.ts`, `store.test.ts`, `storage.test.ts`, `server/permissions/gateIntegration.test.ts`, `server/e2e/claudeWrites.test.ts`, `src/workforce/permissions.test.ts`, `src/workforce/ui/PermissionsPanel.test.tsx`.

**Interfaces:**
- `PermissionRule` gains `workspaceId: string | null` (null = applies in every workspace, as today). `PermissionQuery` gains `workspaceId: string | null`. `appliesTo` requires `rule.workspaceId === null || rule.workspaceId === query.workspaceId`. A rule with a workspace never applies to a query with `workspaceId: null`.
- Storage: a stored rule without the field loads as `null` (old `permissions.json` keeps working, schema version unchanged); a non-string, non-null value makes the file unreadable exactly as other malformed fields do today. `PermissionRuleView` and the browser's validation carry `workspaceId` (missing means null).
- Grants made from an approval (`decideApproval`: scopes `task`, `agent`, `once`) set `workspaceId` to the approving task's workspace id; rules created through `POST /api/permissions` keep `null` unless the body names a registered `workspaceId` (accept an optional `workspaceId`, validate it against the configured workspaces, refuse an unknown one with a fixed sentence). Global defaults stay `null`.
- Every `permissions.evaluate` call in `taskManager.ts` (`approveTool`, `permitTool`) passes the task's workspace id.
- The permission row shows the workspace when the rule has one (for example `Workspace sandbox`), and the revoke label names it.

- [ ] Tests first: engine (a workspace-bound agent rule applies in its workspace and not in another, not when the query has none; precedence and deny behaviour unchanged for null rules), storage (old file without the field loads with null; bad value is rejected), store (grants keep the field; `reconcile` unchanged), `gateIntegration.test.ts` (an `allow_agent` approval in workspace `a` does not allow a write in workspace `b` for the same agent, which asks; the same agent in `a` later still does not ask), e2e (two registered workspaces `sandbox` and `docs`: after `allow_agent` in `sandbox` a write in `docs` asks; a created-by-API rule with `workspaceId: 'ghost'` is refused; one with `sandbox` is accepted and shown), UI/validation tests.
- [ ] Update, deliberately, any existing test that pinned a cross-workspace allow, and say so in the report.
- [ ] Commit `fix(server): task and agent permissions from an approval belong to their workspace`.
